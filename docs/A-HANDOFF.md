# A 的开发与交接手册

你的职责是让用户从问题现场顺利进入一份可信的讨论快照：入口、知乎采集、任务状态、部署与联调。B 负责观点分类质量，C 负责真人交流，D 负责圆桌编排。

## 先运行

```sh
pnpm install
pnpm check:config
pnpm db:migrate
pnpm dev
```

打开终端显示的地址。无凭证时点击“见山另一面”，即可演示总览、讨论区、圆桌和补充材料。实时入口保留清楚的禁用原因。

拿到 Access Secret 后：复制 `.env.example` 为 `.env.local`，在本地编辑器中填入 `ZHIHU_ACCESS_SECRET`，保留默认快速模型，然后重新启动开发服务。不要将实际值填进模板。已有进程环境变量优先于文件设置；使用一种配置来源更便于排错。

```powershell
Copy-Item -LiteralPath .env.example -Destination .env.local
```

`.env.local` 被 Git 忽略。生产环境通过部署平台的服务端凭证配置注入变量，不上传本地文件。`pnpm build` 不将配置值写入构建产物。`ZHIHU_MODEL` 支持 `zhida-fast-1p5`、`zhida-thinking-1p5`；具体权限以团队实际发放为准。

## 前后端契约

统一成功：`{data: ...}`；统一失败：`{error: {code, message, canUsePreset}}`。

| 调用                                 | 返回                                              | 说明                                                                          |
| ------------------------------------ | ------------------------------------------------- | ----------------------------------------------------------------------------- |
| `GET /api/config`                    | 200，配置状态                                     | 不访问知乎，不返回密钥；`configured-unverified` 表示尚未在线验证              |
| `GET /api/visitors/session`          | 200，访客身份 + Cookie                            | 创建任务前先建立身份，防止并行请求生成不同访客                                |
| `GET /api/topics`                    | 200，议题列表                                     | 三个已开放议题；自由议题尚未开放                                              |
| `POST /api/topics`                   | 200，匹配议题                                     | 通过 ID 或已开放标题匹配议题                                                  |
| `GET /api/history`                   | 200，`{results,jobs}`                             | 各最多 20 条，仅当前 Cookie 对应访客可见                                      |
| `POST /api/topics/:topicId/analyses` | 202，`{jobId, job}`；或 200，`{resultId, cached}` | 请求体 `{mode:'live', requestId:UUID}`；预置模式 `{mode:'mock'}` 直接返回结果 |
| `POST /api/jobs/:jobId/run`          | 200，完成/失败任务；或 202，正在运行的任务        | 原子抢占执行权；重复调用不会重发上游请求                                      |
| `GET /api/jobs/:jobId`               | 200，`AnalysisJob`                                | 仅发起任务的访客可读；他人查询/执行返回 404                                   |
| `GET /api/analyses/:resultId`        | 200，`Analysis`                                   | B、C、D 继续沿用现有快照格式                                                  |

示例链路：建立访客 → 创建任务 → 若返回快照则直接打开 → 否则提交一次 `run`，同时轮询 GET → 取得 `resultId` → `/overview?analysis=...`。页面导航继续使用原生链接，保留此前的生产环境修复。

任务状态：`queued → running → succeeded/failed`；实际阶段为 `collecting → classifying → saving → done`。失败保留最后阶段和可公开的错误说明，不保存上游原始错误体、请求头或密钥。浏览器仅保存任务 ID，真实状态在数据库。

## 任务执行边界

当前采用“两步请求”：创建接口立即返回 202；`run` 的 HTTP 请求保持连接并等待实际工作结束，GET 可独立查询进度。这样不依赖无法保证完成的后台 Promise。

**尚未接入持久队列。** 保持执行页打开有助于完成任务；刷新、关闭页面或平台中断后，任务可能已完成，也可能终止。重新进入页面只查询已保存状态，不自动重跑模型；尚未执行的 queued 任务可点“继续这次采集”。运行超过 120 秒、排队超过 10 分钟，下一次查询会将其标为过期并释放占用。迟到结果不能覆盖过期状态。

搜索和模型各有 40 秒请求上限；浏览器执行请求等待 110 秒。业务请求不自动重试。模型超时并不保证未计费，先查原任务，再由用户明确新建。同一访客重复提交复用原任务；不同访客同时采集同一范围返回 `TOPIC_BUSY`，不暴露他人的任务 ID。完成后可复用成功快照。搜索、分类、圆桌与追问都经过实际请求级限额，详见 [A-EXPANSION.md](A-EXPANSION.md)。

面向正式上线的下一步：接入持久队列/工作流，再将 `run` 替换为队列消费者；保留 `AnalysisJob` 与 `resultId` 契约。长时间任务的可靠执行、排队调度及真实耗时仍需在凭证到位后完善。

## 与队友的交接点

| 队友 | A 提供什么                                                         | 对方继续负责什么                                                               |
| ---- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| B    | 标准化 `Source[]`、逐字引用所需摘要、采集阶段回调、存储好的快照 ID | 分类提示词、相关性、分歧与证据校验；修改数据协议时同步更新 `DATA_VERSION`      |
| C    | 稳定的访客 Cookie、`analysisId/categoryId`、新增任务表迁移         | 发帖、回复、点赞、讨论区持久化；本轮未改变原帖子表与接口                       |
| D    | 相同快照和公共任务类型示例                                         | 圆桌角色、回应质量、追问和待解问题；圆桌生成目前仍用原接口，未迁入新任务执行器 |

B 的入口由原 `createLiveAnalysis` 改为 `buildLiveAnalysis(title, onStage, topicId, visitorId)`：只采集并生成经过验证的 `Analysis`；A 的 jobs 模块负责存储、去重、缓存和失败状态。校验规则保持不变。数据库迁移已新增至 `0003_ambitious_eternity.sql`（历史、调用计数、任务议题及旧成功任务历史回填）；所有本地开发者拉取后需运行迁移，不改写之前已部署的迁移。

## 凭证到位后的最小联调

1. 运行 `pnpm check:config`，确认配置存在；这一步不验证权限、不消耗业务额度。
2. 在问题现场点击一次实时采集，观察真实阶段。成功链路包含一次搜索与一次分类模型调用。
3. 打开结果，人工核对摘要、链接、评论作者、引用依据与分类相关性。不要将搜索结果说成“本问题全部回答”。
4. 回到入口再次发起，确认 1 小时内复用快照。刷新进行中的页面，确认能查询同一个任务。
5. 与 D 单独验收一次实时圆桌，核对它是否基于相同快照；这会产生额外模型调用。
6. 记录实际模型、耗时、有效主来源/评论数和发现的问题，不记录密钥。

| 现象                   | A 应检查                                               |
| ---------------------- | ------------------------------------------------------ |
| 实时入口不可用         | 配置文件位置、重启服务、是否有进程变量覆盖、模型白名单 |
| `ZHIHU_AUTH_FAILED`    | Secret、接口授权、服务器时间；不将其误判成无内容       |
| `ZHIHU_RATE_LIMITED`   | 调用频率与账号可用额度，停止连续重试                   |
| `EMPTY_SOURCES`        | 本次结果是否只有问题条目/空摘要；可明确返回预置        |
| `MODEL_OUTPUT_INVALID` | 与 B 检查结构、来源 ID、逐字引用；不展示未经校验的结果 |
| `JOB_EXPIRED`          | 原任务是否断线/超时；不自动再次发起模型 POST           |

## 验收命令与部署

```sh
pnpm typecheck
pnpm test:contracts
pnpm test:entry
pnpm test:smoke
pnpm build
```

`test:entry` 使用隔离 SQLite 和人工响应，测试代码中禁止真实网络；它不证明知乎线上模型质量。`test:smoke` 需要本地服务，会写入“本地验收”帖子。手工界面验收应覆盖：预置跳转、配置加载失败/重查、任务重复提交、刷新恢复、失败后预置回退、成功快照进入讨论与圆桌。

部署仍使用当前 Sites 项目、D1 绑定与原有访问范围。打包时包含新增迁移；先验证本地构建再更新现有站点。比赛对外演示的访问权限需团队单独决定，当前在线 Demo 为所有者私有。
