## 1. 产品理念与定位

“见山另一面”是一款基于知乎真实内容的 AI 观点社交产品。

当用户打开一个回答较多、观点复杂的知乎问题时，可以启动“见山另一面”。AI 将当前采集到的回答、相关内容摘要和精选评论，按照讨论角度、观点立场与核心论据整理为不同讨论区。用户可以进入自己关心的区域，与关注同一议题、同一角度的人深入交流；也可以进入 Agent 圆桌，观看不同观点之间有组织的讨论，理解核心主张、争执过程与真正分歧。

产品的核心理念是把讨论中的“共识”与“争论”分离：

- **分类讨论区**承接共同关心某一角度的用户，支持补充经历、澄清条件、交换证据和深化知识。
- **Agent 圆桌**集中呈现不同观点之间的交锋，以及当前材料支持的共同点、分歧与证据缺口。

两类空间相互连接，帮助用户看见原本忽略的另一面，并为持续交流和知识沉淀创造条件。观点整理是进入讨论的入口；真人交流和跨观点理解共同构成核心体验。

### 1.1 必须保持的产品原则

1. 同一讨论角度允许不同立场存在；分类针对内容，不给用户永久贴标签。
2. 讨论区不强求一致，圆桌不为了戏剧效果制造对立。
3. AI 生成的共同表述不等于作者或用户已达成共识；没有充分依据时明确保留分歧。
4. 真实来源、预置模拟内容、真人发言和 AI 发言必须可以辨认。
5. 每项整理都应帮助用户继续理解或参与具体讨论。

## 2. 目标用户、场景与本次验证目标

### 2.1 首批目标用户

- 正在知乎了解一个复杂问题，希望找到相关角度并参与交流的人。
- 拥有相关经历或证据，希望自己的补充得到针对性回应的人。
- 希望理解不同立场为什么存在、各自依赖什么条件的人。

首版统一演示议题：**普通人现在还有必要学习 AI 编程吗？**

以下分类仅是预置样本的设计方向，真实分析应根据实际材料生成：

| 分类方式 | 示例 | 讨论重点 |
|---|---|---|
| 讨论角度 | 实际用途 | 学习后能解决什么具体问题？ |
| 讨论角度 | 学习投入 | 零基础需要投入多少时间，困难在哪里？ |
| 讨论角度 | 就业与能力 | 做出工具与胜任工作之间有哪些差距？ |
| 观点立场 | 支持从具体任务入手 | 哪些任务值得尝试？ |
| 观点立场 | 强调基础与验证能力 | 哪些基础不能省略？ |
| 观点立场 | 质疑没有目标的学习投入 | 在什么条件下不值得投入？ |

这些立场可能部分重叠，不预设必须形成赞成、反对、中立三等分。

### 2.2 MVP 要验证什么

| 假设 | 应观察到的行为 |
|---|---|
| 分类让讨论更容易参与 | 用户能找到关心的角度，并围绕该角度补充内容 |
| 圆桌帮助理解分歧 | 用户能指出至少一处真实分歧及其适用条件或依据 |
| 两类空间能够相互促进 | 用户从圆桌的待解问题进入讨论区，提交相关经历、条件或证据 |
| 产品具有继续使用的可能 | 用户愿意回应他人，或在后续遇到问题时主动再次使用 |

以上均是待验证假设。MVP 完成不代表已验证长期留存、深度连接或商业价值。

## 3. MVP 范围与交付口径

### 3.1 必做范围

只做四个页面：模拟知乎问题页、分类总览页、分类讨论区、Agent 圆桌页。

完整支持：两种分类切换、查看来源、发布和回复、点赞、一次圆桌讨论、一次追问、从圆桌带着具体问题进入讨论区补充内容，以及查看已补充材料。

保留原版的 Mock 优先策略。四页交互可用预置数据先完成；真实接口最小验证在凭证到位后尽早开展，与页面开发并行。

### 3.2 本次不做

- 真正的浏览器扩展安装、真实知乎页面按钮注入或任意网页抓取。
- 全量回答和评论采集、持续监测所有新回答。
- 用户匹配、关注系统、私信、通知中心和独立个人主页。
- 观点教练、观点胶囊、课程生成或额外的知识库页面。
- 自动把应用内发言发布到知乎。
- 无限轮次 Agent 自由讨论或自动重算已有讨论区的分类。

知乎 OAuth、自由输入任意问题、热榜选题、自动生成讨论纪要均为后续增强，不阻塞四页 MVP。第一版的跨用户交流使用本应用访客身份。

### 3.3 分开验收两种交付状态

- **交互交付**：四页在公网可操作，预置来源和预置圆桌可稳定演示；两名访客可通过共享后端发帖和回复。
- **真实接入验证**：团队凭证下完成一次官方搜索、一次分类生成及一次有来源依据的圆桌生成，记录实际模型权限、返回字段和失败行为。

凭证尚未到位时可交付明确标注的预置演示版，真实接入项保持“未验证”；不得把模拟流程描述成已完成实时知乎分析。

## 4. 官方能力与内容边界

依据官方 `zhihu` skill `0.5.3-beta.20260904115023`。以下是这版文档的能力描述，实际授权、额度和稳定性需通过团队凭证核验。

| 能力 | 官方支持 | 对本产品的约束 |
|---|---|---|
| 知乎搜索 | 关键词搜索；单次最多 10 条；`HasMore` 固定为 `false` | 无文档支持的问题 ID 过滤、全部回答遍历或翻页能力 |
| 搜索内容 | 问题、回答、文章；`ContentText` 为摘要 | 问题条目不作为观点来源；不能把摘要当完整原文 |
| 精选评论 | 可选 `CommentInfoList`；只保证评论内容字段 | 不保证有评论作者、独立 ID 或直达链接 |
| 知乎直答 | `model`、`messages`、`stream` | 分类、角色编排、结构解析和来源校验由应用实现 |
| 上下文对话 | 文档明确列出 `zhida-fast-1p5`、`zhida-thinking-1p5` | 以实测权限选择；不假设 `zhida-agent` 等同可控的多角色框架 |
| OAuth | 知乎账号授权及相关用户数据 | 可选；不能替代应用自己的讨论、回复和点赞后端 |
| 赛事故事与知识接口 | 比赛配套内容列表及详情 | 不能代替知乎问题下的回答集合，首版不纳入核心链路 |

### 4.1 分析范围必须与来源相符

默认真实接入模式是“围绕当前问题检索相关知乎内容”。界面显示：

> 围绕这个问题，整理当前检索到的知乎回答、文章摘要与精选评论。

每条主来源记录其与当前问题的关系：本问题下、相关内容、归属未确认。只有通过来源链接或其他明确元数据确认归属，才标记“本问题下”；标题相似不构成归属证明。

若提供“仅本问题下”范围，必须过滤掉相关内容和归属未确认内容。样本不足时如实展示，不自动补入其他问题的内容。

### 4.2 来源与生成模式分别标注

| 维度 | 模式 | 页面说明 |
|---|---|---|
| 来源 | `live` | 本次实时检索的真实来源，显示采集时间 |
| 来源 | `snapshot` | 预置真实来源样本，显示原采集时间 |
| 来源 | `mock` | 团队编写的模拟样本，明确标记“模拟内容” |
| 生成 | `live` | 本次 AI 生成 |
| 生成 | `cached` | 已保存且通过校验的 AI 整理结果 |
| 生成 | `scripted` | 团队预置的演示整理或圆桌脚本 |

同一个分析快照不混入模拟与真实来源。模拟作者不能冒充真实知乎作者，模拟文本不能挂上不对应的真实原文链接。真实来源快照的原文链接、采集时间和来源归属必须保留。

## 5. 用户主流程

```text
模拟知乎问题页
  → 点击“见山另一面”
  → 采集或载入样本 → AI 整理或载入预置结果
  → 分类总览
       → 选择讨论角度或观点分类
           → 真人讨论区：查看来源 → 补充观点/经历/条件/证据 → 回复他人
       → Agent 圆桌：开场 → 陈述 → 交锋 → 总结 → 可追问一次
           → 选择“补充这个问题”
           → 对应讨论区：带入待解问题 → 发布补充 → 展示为已补充材料
```

往返时保留议题、分析快照、分类和圆桌上下文。返回按钮回到原位置，不重新触发分析或丢弃输入草稿。

## 6. 四个页面的功能要求

### 6.1 页面一：模拟知乎问题页｜负责人 A

**目标：让用户理解启动入口，并知道本次将整理哪些内容。**

- 展示统一演示议题、少量来源预览和“见山另一面”按钮；明确这是演示页面。
- 点击后展示实际阶段：采集或载入样本、整理观点、准备讨论区。没有真实进度时不显示伪精确百分比。
- 分析完成后进入对应快照的分类总览。
- 未配置凭证时直接提供预置演示入口；不展示成实时检索成功。
- 接口失败、样本为空或分类失败时保留失败原因，并提供返回与预置演示入口。
- 同议题存在有效预置样本时可以使用该样本；切到统一演示议题时同步更新标题、链接和路由。

**验收：**从入口可进入总览；分析中不能重复创建同一任务；失败后可明确切换预置演示，显示的议题始终与样本一致。

### 6.2 页面二：分类总览｜负责人 B

**目标：帮助用户选择想深入讨论的区域，同时理解整体分歧。**

- 默认显示“按讨论角度”，可切换“按观点立场”；两种分类都能进入对应讨论区。
- 分类卡片展示名称、讨论说明、一个具体待讨论问题、来源数量、来源占比和 1—2 条代表材料。
- 演示样本覆盖约 3 个角度和最多 3 个立场；真实结果按材料生成，不强行凑齐。
- 显示“当前材料中的共同点”“主要分歧”“还缺什么信息”，每项关联依据；允许没有明确共同点。
- 共同点仅表示材料中的重合表述，不宣称作者已相互确认或所有人都同意。
- 代表材料可以展开摘要、查看所属来源与知乎原文；评论通过父来源追溯。
- 提供“进入讨论区”和“进入圆桌”按钮；内容不足以形成两种有依据的观点时，说明圆桌暂不具备条件。

**计数口径：**按去重后实际纳入分析的回答与文章计数；问题条目不计入，精选评论作为补充材料不单独增加分母。某分类引用评论时，映射到其父来源后去重计数。跨分类允许重叠，数量和比例由程序计算。

卡片示例：“8 条来源中有 3 条涉及此观点”。旁边显示“仅代表当前采集样本；分类可能重叠，占比不一定合计为 100%”。

**验收：**用户能找到一个关心的角度并进入讨论；任一分类都能查到支撑材料；两个标签页切换不改变总样本口径。

### 6.3 页面三：分类讨论区｜负责人 C

**目标：围绕一个明确角度，产生有针对性的补充和回应。**

- 顶部固定显示分类说明、当前讨论问题、代表来源和“允许不同立场参与”的提示。
- 浏览无需登录；第一次发言使用本应用访客身份，可设置显示昵称。身份不冒充知乎账号。
- 发言可选择“观点”“亲身经历”“适用条件”“证据补充”，默认“观点”，不强迫填写长表单。
- 编辑框根据类型给出简短提示，例如经历发生的背景、建议适用的条件；证据补充可选择已有来源或填写公开链接。
- 支持发布、一级回复、点赞和取消点赞。回复须关联原帖；同一访客对同一帖仅有一个点赞状态。
- 同时区分用户本次发布、预置演示发言和 AI 内容；不把预置账号显示为正在在线互动的真人。
- 发布成功后立即显示；失败保留草稿。刷新或另一浏览器访问时可读取共享后端中的帖子。
- 从圆桌进入时，顶部带入具体待解问题，编辑框保留用户草稿；发布后帖子关联该问题。
- 页面内“已补充材料”区域列出与圆桌问题关联的帖子，保留作者、回复和引用入口。这是首版的知识沉淀方式，不自动判断证据已充分。
- 可返回总览、进入圆桌或打开原文。

**验收：**两名不同访客可完成发布与回复；一条从圆桌带来的待解问题能得到相关补充，并在刷新后仍可查阅。

### 6.4 页面四：Agent 圆桌｜负责人 D

**目标：基于已采集材料，有组织地展示观点如何回应彼此，并把尚未解决的问题交回真人讨论。**

- 预置演示使用三个观点角色和一个主持人。真实模式使用 2—3 个有依据的观点角色，不足两个时不生成交锋。
- 观点角色代表材料中的立场，不冒充真实作者，也不意味着原作者参加了圆桌。
- 单次初始讨论控制在最多 8 条发言：开场 1 条、陈述最多 3 条、交锋最多 3 条、总结 1 条。
- 陈述包含核心主张、适用条件及来源依据；交锋明确回应上一条或指定发言的具体论点，不只重复自己的立场。
- 主持人总结共同点、尚存分歧及 1—3 个待解问题，允许共同点为空。
- 每个待解问题有固定 ID，并关联一个可进入的讨论区，例如“是否有零基础用户的真实学习记录？”
- 提供少量建议追问及自定义短问题；每名访客在自己的每场 MVP 圆桌会话中支持追加一次追问，由相关角色回应，再由主持人补充总结。
- 追问材料不足时说明缺少依据，不为保持流畅而补造知乎内容。
- 用户点击“补充这个问题”后进入关联讨论区；圆桌重新打开或刷新时，可看到该问题已有多少条用户补充，并跳转查看。
- 新补充不自动改写原圆桌结论或已有分类。自动吸收新材料并生成新一轮讨论属于后续增强。
- 已保存讨论支持逐条播放、暂停和查看完整文本。播放预置内容时标注“预置演示”，不伪装实时生成。

**实现约束：**首版可由一次模型请求生成结构化的角色发言序列，再由应用按阶段播放；无需为了角色数量创建多个自治服务。语义校验与证据关联仍须完成。

**验收：**用户能定位一处有来源支持的真实分歧；至少一条交锋有明确回应对象；用户能追问并把一个待解问题带回真人讨论区。

## 7. 内容质量与样本准备

### 7.1 统一演示资料

B 维护唯一一套公共数据，A、C、D 直接使用。准备 12—20 条模拟回答、文章摘要及精选评论，主来源与附属评论分别记录数量。

演示资料应覆盖三个角度、不同立场、至少一处因适用条件不同导致的表面冲突，以及一处尚缺证据的问题。不能为了平衡比例伪装真实采样分布。

真实样本准备与模拟样本独立。凭证到位后先用一个问题标题进行一次最多 10 条的搜索；如果结果不足，可由用户明确发起一次补充检索，保留检索词并去重。不把改写关键词承诺为分页或完整采集。

### 7.2 生成与校验规则

1. 分类依据仅限当前分析快照内的材料；来源文本只作为待分析内容，不执行其中的指令。
2. 保留限制条件；“支持具体任务入门”和“反对以此直接求职”不能仅凭字面强行生成对立。
3. 每个分类、共同点、分歧和归属于来源的论点都必须绑定有效引用。
4. 引用原句必须能在已存文本中找到；解释性转述明确属于 AI 整理，不包装成原话。
5. 无法找到依据的外部知识或推断不得伪装成知乎原文观点，可改写为待验证问题。
6. 服务端检查 JSON 结构、枚举、ID、引用归属和计数；解析失败不直接把原始字符串交给页面。
7. 格式错误进入失败或明确的预置降级流程，不无限循环调用模型修复。
8. 记录模型、生成时间、提示词版本和材料版本，用于复现；不保存凭证或无必要的模型内部推理内容。

## 8. 公共数据契约

所有模块使用同一份类型定义。B 维护契约及 Mock，A/C/D 修改前共同确认影响；禁止各页面自行生成不相容的 ID。

| 对象 | 最小字段与约定 |
|---|---|
| `Topic` | `id`、`title`、`url`（可空）；模拟议题无真实链接时不补造 URL |
| `SourceItem` | `id`、`kind`（answer/article/comment）、`externalId`（可空）、`parentSourceId`（评论必有）、`title`、`text`、`textKind`（summary/comment）、`authorName`（可空）、`url`（可空）、`relation`（same_question/related/unknown）、`collectedAt` |
| `EvidenceRef` | `sourceId`、`excerpt`；指向快照内有效来源，摘录必须存在于该来源文本中 |
| `Category` | `id`、`analysisId`、`type`（dimension/stance）、`name`、`description`、`discussionQuestion`、`sourceIds`、`evidenceRefs`、`sampleCount`、`sampleRatio` |
| `Finding` | `id`、`text`、`categoryIds`、`evidenceRefs`；用于共同点、分歧和总览待解问题，所有引用属于同一快照；待解问题的引用表示提问背景，不表示答案已有证据 |
| `AnalysisSnapshot` | `id`、`topicId`、`sourceMode`、`generationMode`、`scope`（same_question_only/related_topic）、`queries`、`collectedAt`、`createdAt`、`version`、`sources`、`categories`、`commonGround`、`disagreements`、`openQuestions`、`sampleCount`、`commentCount`；实时或缓存 AI 结果附模型及提示词版本 |
| `Visitor` | `id`、`displayName`、`createdAt`；ID 由服务端会话确定，不接受请求伪造作者身份 |
| `DiscussionPost` | `id`、`analysisId`、`categoryId`、`authorId`、`authorName`、`content`、`contributionType`（opinion/experience/condition/evidence）、`parentPostId`（可空）、`gapId`（可空）、`sourceIds`、`externalEvidenceUrl`（可空）、`origin`（user/seed）、`voteCount`、`createdAt`；查询响应另含当前访客 `likedByMe` |
| `Roundtable` | `id`、`analysisId`、`visitorId`、`status`（preparing/ready/failed）、`generationMode`、`roles`、`messages`、`commonGround`、`disagreements`、`gaps`、`followupUsed`、`createdAt`；角色含 `id/name/categoryId/sourceIds`，主持人的 `categoryId` 可空；模型生成结果另存模型及提示词版本 |
| `RoundtableMessage` | `id`、`roundtableId`、`speakerRoleId`、`phase`（opening/statement/exchange/summary/followup）、`content`、`replyToMessageId`（可空）、`evidenceRefs`、`order` |
| `DiscussionGap` | `id`、`roundtableId`、`question`、`categoryId`、`contextEvidenceRefs`；`supplementCount` 为关联用户帖数量，服务端计算，不作为问题已解决的判断 |
| `AsyncJob` | `id`、`kind`（analysis/roundtable/followup）、`status`（queued/running/succeeded/failed）、`stage`、`resultId`（可空）、`errorCode`（可空） |

### 8.1 ID 与快照约定

- 所有 ID 均为字符串。真实主来源按 `ContentType + ContentID` 去重，保留原始溯源链接；模拟来源使用独立命名空间。
- 精选评论使用父来源加评论文本生成本地 ID，仅表示应用内标识；不声称是知乎官方评论 ID。
- 评论缺少作者时显示“精选评论”；查看原文通过父来源跳转。
- 分类是快照内的内容组织结果；讨论区唯一定位为 `analysisId + categoryId`。
- 已有帖子的快照不可原地改分类。重新分析创建新快照，旧帖子、圆桌和链接保留在原快照。
- 本轮 MVP 预置快照固定，不做历史讨论迁移或跨快照合并。
- 分类的 `sourceIds` 是引用材料列表；计数时把评论映射到父来源后去重。`sampleRatio` 为分类主来源数除以快照主来源总数；总数为零时不产生比例。
- `gapId`、回复关系、引用和角色关联必须由服务端检查，不能跨议题、跨快照或跨讨论区错连。
- 待解问题的直接补充帖计入 `supplementCount`；普通回复不自动重复计数。

## 9. 应用接口与后端边界

以下均为本产品自建接口，与知乎官方接口分开。前端不直接携带 Access Secret 调用知乎。

| 接口 | 作用 | 负责人 |
|---|---|---|
| `POST /api/visitors/session` | 创建或恢复访客会话、设置显示昵称 | C |
| `POST /api/topics` | 创建或复用议题，接收标题和可选来源 URL | A |
| `POST /api/topics/:topicId/analyses` | 选择来源模式及范围，启动或复用分析任务 | A 编排、B 分析 |
| `GET /api/jobs/:jobId` | 返回异步任务状态与结果 ID | A 提供公共能力，D 接入 |
| `GET /api/analyses/:analysisId` | 返回固定分析快照及来源 | B |
| `GET /api/analyses/:analysisId/categories/:categoryId/posts` | 获取讨论及关联补充，可按 `gapId` 筛选 | C |
| `POST /api/analyses/:analysisId/categories/:categoryId/posts` | 发帖或回复，作者来自服务端会话 | C |
| `PUT /api/posts/:postId/like` | 设置 `liked: true/false`，重复请求不增加额外票数 | C |
| `POST /api/analyses/:analysisId/roundtables` | 启动或复用圆桌任务 | D |
| `GET /api/roundtables/:roundtableId` | 查询圆桌、追问结果及待解问题补充数量 | D，C 提供补充计数 |
| `POST /api/roundtables/:roundtableId/followups` | 提交一次追问，完成后追加到同一圆桌 | D |

### 9.1 通用约定

- 查询成功返回 `{ data }`；创建任务返回 HTTP 202 与 `{ data: { jobId } }`，缓存已就绪时可返回 HTTP 200 与 `{ data: { resultId } }`。
- 错误返回 `{ error: { code, message, canUsePreset } }`；不把鉴权失败表示为搜索无结果。
- 发布帖子与创建任务使用客户端请求 ID 去重；模型请求超时后不自动重复发送同一请求，也不循环轮询失败任务。
- 字段缺失、空白发言、越界回复、无效来源和不存在的分类返回明确错误。发言最长 2000 字，追问最长 300 字，访客昵称最长 20 字。
- MVP 单页显示最多 50 条讨论，更多内容通过游标继续加载；回复关系仍完整保留。无需实时推送，另一访客刷新即可看到更新。
- 发帖、回复和点赞存入共享持久化存储；不能仅依赖组件内存或浏览器本地存储完成双访客验收。
- 前端沿用 React、TypeScript、Tailwind 和团队已有组件。A 在开工时锁定共享后端、持久化部署方式和数据库迁移入口；C 负责讨论相关存储实现。
- 官方搜索和直答调用在服务端完成；模型访问封装由 D 维护，B 复用以完成分类。
- MVP 只用官方文档支持的模型请求字段，不假定 `response_format`、工具调用或结构化输出约束生效。
- 搜索与分类按议题、范围、查询和数据版本缓存；基础圆桌结果按分析快照缓存。不同访客从缓存创建各自的圆桌会话副本，分配对应的消息和待解问题 ID，追问额度互不影响；同一会话刷新不重新生成。圆桌入口可静默创建访客会话，仅在发言时要求设置昵称。
- 本应用发言只在本应用内发布。内容以安全文本渲染，链接仅允许 HTTP(S)，服务端限制异常高频提交。

### 9.2 凭证与团队准备

按团队转发通知，系统建队是队长领取赛事 token 的前置事项。队长负责确认建队和凭证发放状态；具体日期以活动页面及官方最新通知为准。

收到凭证后先确认它属于 Access Secret、OAuth App Key、OAuth 用户 Token，还是其他赛事资源。不同凭证不混用，也不预设团队额度等同文档中的默认邀测额度。

Access Secret 及其他私密凭证仅放在后端或部署平台的安全凭证配置中，不写入前端包、源码、文档、日志或代码仓库。OAuth 为可选增强；当前访客模式不读取用户知乎创作、关注或收藏。

## 10. 加载、失败、空数据与降级

| 场景 | 页面行为 |
|---|---|
| 未配置凭证 | 显示预置演示入口，说明尚未启用实时采集 |
| 搜索返回空结果 | 显示当前没有可分析来源，允许返回或选择预置演示 |
| 只有问题条目或无关来源 | 不生成虚构分类；显示材料不足 |
| 没有精选评论 | 正常展示回答或文章，不补造评论 |
| 没有作者或独立评论链接 | 作者按未知处理，评论通过父来源查看原文 |
| 找不到两种有依据的观点 | 保留总览与真人讨论区；圆桌解释暂无法形成交锋 |
| 模型输出格式或引用无效 | 不发布该结果，提示整理失败并提供可用的预置入口 |
| 上游超时、鉴权失败或额度不足 | 停止自动重复请求，显示适当原因；保留已存在的有效结果 |
| 从其他议题切到演示数据 | 明确切换到演示议题，标题、样本、路由和模式标签同步更新 |
| 发帖或点赞失败 | 保留输入或恢复原点赞状态，允许用户在失败明确后重试 |
| 深链接指向不存在的快照或分类 | 显示可返回议题入口的空状态，不打开另一分类冒充结果 |

预置演示与真实采集使用相同的数据契约，但模式标签、采集时间和来源归属必须真实。不能把每次失败都静默转换成“分析成功”。

## 11. 统一交互与视觉要求

- 蓝白主色调，统一卡片、按钮、字体、间距和加载样式。
- 首屏优先显示议题、当前角度或争议和主要操作，避免同时堆叠全部分类、对话和说明。
- 真人发言、AI 角色和模拟内容除颜色外还要有文字标签。
- 入口与总览持续显示样本范围；讨论区和圆桌可一键展开来源说明。
- 每页都有明确返回路径；跳到原文后用户可继续当前讨论。
- 从圆桌跳转讨论区时，目标问题应直接可见，输入框不要求用户重新描述上下文。
- 支持桌面浏览器和手机宽度；键盘可操作标签页、按钮及输入框，输入项有可识别标签。
- 模拟数据标签、作者未知、样本不足等说明应简短清楚，不向产品用户暴露调试堆栈或接口字段。

|---|---|---|---|
| A | 模拟问题页、议题入口、官方搜索、公共任务状态、后端部署与最终集成 | 页面一、来源适配、运行环境、部署地址 | 与 B 锁定来源结构；与 C 确保持久化；与 D 接通任务结果 |
| B | 分类总览、公共契约与样本、分类生成、计数和引用校验 | 页面二、共享类型、Mock/真实样本快照、分析接口 | 复用 A 的来源和 D 的模型封装 |
| C | 真人讨论区、访客会话、发帖回复点赞、补充材料沉淀 | 页面三、讨论接口与存储、双访客验收 | 复用 B 的分类 ID；接收 D 的待解问题 ID |
| D | Agent 圆桌、统一模型访问、角色编排、追问与待解问题 | 页面四、模型封装、圆桌脚本及接口 | 使用 B 的同一快照；与 C 完成补充计数与跳转 |

A 负责最终集成，不代表其他人的接口由 A 代写。各负责人同时完成页面、所负责的数据或接口及相应验收。

B 是公共数据契约维护人；涉及字段或 ID 的变更须同步给其他三人。公共模型封装、路由和组件的修改指定单一负责人，避免互相覆盖。

## 13. 开发顺序与停止条件

### 阶段一：冻结共同约定

- 确定统一演示题、四页路由、访客模式、数据契约和样本统计口径。
- A 锁定后端及持久化部署方式，B 提交共享类型与首套样本，C/D 确定 `gapId` 的传递和存储方式。
- 检查团队建队及凭证状态；不在这一阶段新增页面。

### 阶段二：四页用 Mock 并行开发

- A/B 跑通入口到总览，C 实现跨访客发布与回复，D 完成固定样本圆桌。
- 同时联调分类 ID、返回路径和真实/预置标签，不等到最后才合并页面。

### 阶段三：凭证到位即做最小真实验证

- 搜索一次统一议题，检查来源类型、摘要、链接、评论和实际数量。
- 用实际可用模型生成一份分类快照和一场短圆桌，检查解析、引用、耗时及权限。
- 通过校验的真实结果可存为明确标注采集时间的预置真实快照。
- 若验证失败，记录具体失败点并保持预置演示可用；不声称实时模式完成。

阶段三可与阶段二并行；无凭证时不阻塞交互开发。

### 阶段四：连接两个讨论空间

- 圆桌输出待解问题并定位到具体分类。
- 用户在讨论区提交补充，关联待解问题。
- 讨论区展示已补充材料，圆桌可查看补充数量与跳转入口。

### 阶段五：验收、试用与交付

- 在部署地址完成下节验收，检查手机宽度及另一浏览器的访问。
- 进行少量真实用户试用，修正最明显的理解和参与障碍。
- 准备产品说明及必要演示材料，标明实时接口的实际完成状态。

四页核心闭环、双访客互动和错误降级通过后停止增加功能。新增 OAuth、自动纪要、关注或匹配不优先于修复现有阻断。

## 14. 验收清单

### 14.1 必须通过的交互与内容验收

- [ ] 公网地址在另一台电脑可以打开四个页面并完成连续操作。
- [ ] 入口显示的议题与实际使用的样本、原文链接和模式标签一致。
- [ ] 两种分类能切换，默认按讨论角度；分类卡片可进入正确讨论区。
- [ ] 样本统计程序计算，来源去重，评论不重复增加分母；零样本不出现错误比例。
- [ ] 每个分类及归属于来源的论点可以找到相应材料；无作者的评论未被错误归属。
- [ ] 两名不同访客可完成发帖、回复、点赞和取消点赞；重复操作不产生重复票数。
- [ ] 帖子刷新后仍存在，另一浏览器可读取；失败保留草稿。
- [ ] 圆桌完成开场、陈述、交锋和总结；至少一处交锋明确回应另一观点。
- [ ] 圆桌提供一次追问，无材料支撑时说明证据不足。
- [ ] 至少一个待解问题可带入正确讨论区，用户补充后关联关系和补充数量可查询。
- [ ] 新增帖子不会悄悄修改已有分类、来源比例或旧圆桌结论。
- [ ] 预置真人发言、实际访客发言、AI 发言、模拟来源和真实来源可以辨别。
- [ ] 测试空来源、无评论、模型失败、发帖失败和无效深链接后，仍有可理解的恢复路径。
- [ ] 发布端没有暴露凭证；用户输入按安全文本呈现。

### 14.2 真实接入单独记录

- [ ] 记录官方搜索成功返回及实际字段，没有将搜索摘要当作完整原文。
- [ ] 记录分类生成和圆桌生成所使用的实际可用模型，结果通过结构与来源校验。
- [ ] 验证缓存复用，不因刷新页面重复调用上游。
- [ ] 记录鉴权、额度或模型权限尚未解决的问题；未验证项保持未勾选。

### 14.3 演示脚本

1. 展示统一议题并启动“见山另一面”，说明当前模式与样本范围。
2. 在总览选择“学习投入”，查看一条来源和当前待讨论问题。
3. 访客甲发布一条带背景的经历，访客乙给予针对性回复。
4. 进入圆桌，看三个有材料支持的角色陈述、交锋，并追问一次。
5. 主持人提出一个缺少真实经历或证据的问题。
6. 点击“补充这个问题”，返回关联讨论区发布补充，展示已补充材料。
7. 返回圆桌或刷新，确认补充数量与跳转入口存在。

模拟圆桌与预置帖子需在演示中保持标注；两位访客实际提交的内容作为本次交互展示。

## 15. 用户试用与产品判断

邀请约 8—12 名近期阅读过复杂知乎问题、或有相关经历愿意交流的人试用。此样本仅提供方向性反馈，不用于证明市场规模或长期留存。

观察：用户能否在约一分钟内选择一个关心的角度；能否说清一处真实分歧；是否愿意贡献相关经历、条件或证据；另一人能否针对该内容回应；圆桌的问题是否促成有效补充。

“有效补充”的人工评估标准：与当前问题相关，至少增加一项可辨认的经历、适用条件或依据；不以长度、赞同主持人或单纯赞同数量代替质量。

记录分母及具体案例，区分有明确任务提示和自主发生的行为。首次试用后保留入口，观察自愿再次使用；不把完成一次指定操作当作自然留存。

如用户只消费总览、不参与讨论，应回到讨论主题、参与动机及回应机制继续验证；不能据此宣称观点社交已成立，也不自动删除既定的社交定位。
